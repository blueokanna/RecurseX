# PARR —— 预测核心

「Predictive Adaptive Recursive Resolver」是整条反馈回路的名字：解析器**测量**查询流和上游
行为，并用这些测量**调优**自己的缓存与传输策略。回路分四段。

```
┌─────────────────┐     ┌──────────────────┐     ┌────────────────────────────┐
│ 查询状态估计器   │────▶│ 解析规划器        │────▶│ 缓存 / 预取 / 并行 /        │
│ (estimator.rs)  │     │ (planner.rs)     │     │ 自适应解析器 (resolver.rs)   │
└─────────────────┘     └──────────────────┘     └────────────────────────────┘
        ▲                                                     │
        └────────────── 观察结果回填 ───────────────────────────┘
```

## 第一段 —— 查询状态估计器

DNS 查询不是独立事件：有时段结构（办公室 9 点打 `mail.example.com`，批处理半夜跑）、短期
突发、长期流行度。每个域 apex 上，估计器维护：

- **时段画像**：96 个 15 分钟桶，统计查询次数；
- **短期 EWMA 速率** + 最近时间戳环形缓冲；
- **流行度**（归一化速率）；
- **观测到的上游成本**（解析 RTT 的 EWMA）。

它回答规划器需要的两个问题：

- `P(接下来 Δt 秒内这个域会被查询)` —— 由时段画像加近期加成算出；
- 该域的归一化流行度，供缓存准入使用。

内存有界：`max_domains` 限制追踪的域数，按陈旧度淘汰。估计器是纯 `no_std`。指数衰减用自带的
`exp`（不用 `libm`——不在允许的依赖集里），精度预算约 1e-11 相对误差。

## 第二段 —— 解析规划器

规划器对每种缓存结果只回答一个问题。注意它**不再**问哪个：流行度决定什么**值得**刷新，
从不决定什么**可以安全**返回。这是两本不同的台账，把它们混为一谈正是风险约束模型要修掉的错误。

| 结果 | 计划 | 由谁决定 |
|------|------|---------|
| 条目仍在存活期 | `ServeFresh` | 条目自身的 TTL |
| 条目已过期、在 stale 窗口内 | `ServeStale { refresh_in_background }` | 风险模型 |
| 未命中，或 stale 被拒 | `Resolve` | —— |

对 stale 条目，规划器算出风险

$$R = V \cdot (1 - P_{\text{LCB}}) \cdot C \cdot \kappa$$

并且**四条全满足**才服务 stale，否则退回 `Resolve`：后果分级本身允许 stale；stale 时长在该等级的
地平线内；答案的保守新鲜度越过 `1 - (1 - \text{base}) / C`；过度服务台账还有额度。`V` 是预期省下的
延迟——一个只值 20ms、且只有 99% 概率正确的答案，不值得用 1000 倍的代价去替一个坏答案辩护。
推导见 [刷新理论](Refresh-Theory-zh.md)。

`Prefetch` 不是一个计划。它是维护循环单独查询的一份策略：一个条目成为预取候选，需要它的模型至少有
`min_evidence_secs`（300 秒）的**真实暴露量**、查询足够可能（未来 60 秒内 `p >= 0.5`）、且当前时刻
离过期足够近，以至于现在刷新能买到目标新鲜度（0.9）。横向的"会不会被问"来自估计器，纵向的
"它会不会变"来自危险模型。默认值：`min_evidence_secs = 300`、`prefetch_horizon_secs = 60`、
`prefetch_min_probability = 0.5`、`prefetch_target_freshness = 0.9`。

那一步只是**放行**一个候选。**下一个令牌该给哪个已放行的候选，是另一个问题**，它由
[信息价值](Value-of-Information-zh.md)回答：每个到期条目用「再观测一次能削减多少风险」定价，预算
流向价值最大的那些。

规划器是无状态的——它消费的每个数字都在危险模型、估计器或缓存里。它唯一触碰的可变状态是风险台账，
而且是显式传入的，方便调用方检查或重置。

## 第三段 —— 变化率模型与缓存

见[缓存准入](Cache-Admission-zh.md)与[刷新理论](Refresh-Theory-zh.md)。PARR 的关键点：
**缓存绝不下发预测的 TTL。** 权威给的那个数字原样发出去，模型只决定**内部**时机与准入。

模型比 EWMA 分数多出来的东西是一个**可测的**量。TTL 是一句声明；一个 RRset 在一段被测量的暴露里究竟
变了几次，才是一次测量。估计器的流行度说的是这个名字**被问**得多不多，危险模型说的是这份数据
**会不会动**。两者正交，而维护循环两个都要：只有流行度没有变化率，会永远预取那些不会变的记录；
只有变化率没有流行度，会把刷新预算花在没人问的名字上。

## 第四段 —— 自适应解析器

上游选择按权威自适应（[上游选择成本模型](Upstream-Selection-zh.md)），别名依赖图
（[别名依赖](Alias-Dependency-zh.md)）让一次刷新决策覆盖整条 CNAME 链，而不是只覆盖其中一跳。
两者都把观测结果回填给估计器和上游模型，闭环。

## 让一切诚实的一条规则

所有预测只调**内部时机和准入**——绝不改发给客户端的字节。权威说 TTL 300 且数据一个月没动，
我们可能提前后台刷新、可能在短窗口内给 stale，但应答里的 TTL 字段仍然是权威说的那个值。
这正是 PARR 作为「正确 DNS 之上的策略层」而非「撒谎的缓存」的原因。
